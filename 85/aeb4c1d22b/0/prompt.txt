  ## 2. Findings
  
  ### F1 `release-ships-rust`: tagged releases build the frozen Rust tree, not burpsy-go
  **Severity:** blocker, but latent. It fires on the first `v*` tag. The shallow clone shows no tags, so I could not confirm whether one has already been pushed on the remote.
  
  **Evidence.**
  - `.github/workflows/release.yml:48` runs `cargo build --release --locked -p burpsy-cli` and packages the result as `burpsy`. Comments at :39 refer to `crates/web/build.rs`.
  - No Go release path exists. The only `go build cmd/burpsy` and goreleaser hits are in nightly.yml and scripts.
  - The last commit touching `crates/` is dated 2026-10-12. AGENTS.md:26 describes `crates/` as "Frozen reference ... do not build new features here".
  
  **Consequence.** Users who download a release get the oracle, which lacks everything built in the Go tree since the freeze. The house rule says a partial result presented as complete is a defect, and this is that defect at release level.
  
  **Options.**
  - (a) Rewrite release.yml to build Go `cmd/burpsy` (and `burpsy-mcp`) for linux/darwin/windows, using CGO-free sqlite.
  - (b) Remove the tag trigger until (a) exists.
  - (c) Keep Rust releases as named "reference" builds.
  
  **Recommendation:** (b) today, (a) next. Desktop/Wails builds can stay out of the release until F3 is fixed.
  
  ### F2 `scanconfig-persist-format`: saved scan settings use Go field names, and restore starts from an all-off config
  **Severity:** major. It silently reduces scan coverage and is a format-compatibility defect.
  
  **Evidence.**
  - `persist.go:2609-2614` saves with `json.Marshal(scanner.ScanConfig)`. `ScanConfig` (scanner.go:159-527) has 68 fields and only 4 json tags: two `json:"-"` and `only_rows`. The on-disk keys are therefore Go identifiers such as `CheckCookieAttributes`.
  - `persist.go:2625` loads into a fresh `&scanner.ScanConfig{}`, so every key missing from the saved JSON comes back as Go's zero value (false or 0).
  - `web/project_state.go:28-31` uses that result to replace the launch baseline outright (`next = cloneScanConfig(*saved)`).
  - The default-on switches are set in `NewActiveScanner` (scanner.go:608-650): CheckActiveInjection, CheckReflectionProbes, CheckXXE, the passive families, and others.
  - No test opens a saved configuration that is missing a key. The only tests that read it back are in web/api_scanner_config_test.go:133 and :387 and :525, and they all save and load with the same build.
  - This is a code reading; I did not run it.
  
  **Consequence.**
  - Every switch added later with a default of `true` comes back **off** for every project saved before it existed. The coverage tracker then reports a smaller check set as if the operator had chosen it.
  - Renaming a Go field silently drops the operator's saved override, because `json.Unmarshal` ignores unknown keys.
  - The persisted format now depends on a scanner type, which is also why persist imports scanner.
  
  **Options.**
  - (a) Persist the wire view that already has stable snake_case keys (`scannerConfigView` / `scannerConfigBoolKeys`, api_scanner_config.go:94/336), and restore by decoding onto a clone of the baseline. Absent keys then keep their defaults.
  - (b) Keep the Go struct, add json tags to all fields, and decode onto the baseline.
  - (c) Store only the keys that differ from the defaults.
  
  **Recommendation:** (a). Add a migration that rewrites old `scanconfig.overrides` into the new form, and a test that opens a document missing a key. That also removes persist → scanner.
  
  ### F3 `desktop-composition-drift`: two hand-copied wiring entry points, and the desktop one has fallen behind
  **Severity:** major.
  
  **Evidence.**
  - `cmd/desktop/main.go:3-6` says it "deliberately duplicates the subset of cmd/burpsy/main.go's wiring".
  - Desktop uses 14 distinct `With*` setters against 52 in cmd/burpsy. It is missing 38, including WithPersist, WithCACertPEM, WithMatchReplace, WithProxyServer, WithExtensions, WithUpstreamProxy, WithNetAuth, WithStreaming, WithServerCerts and WithFileLog.
  - The `-db` flag is parsed at :253 and stored at :60, but `a.dbFile` is never read. DESKTOP.md:104 records this as a known gap ("accepted but not wired").
  - scanner.go:611-614 records an earlier divergence of the same kind: "A separate 30s was the desktop/CLI budget fork."
  
  **Consequence.** Every new capability has to be wired twice. In practice it is wired once, and the desktop build quietly offers less while showing the same UI, because the UI is served by the same `web.Server`.
  
  **Options.**
  - (a) Create `internal/app.Build(Options) (*App, error)` that returns a wired store, proxy, web server and persistence, and call it from both binaries.
  - (b) Have desktop run `cmd/burpsy` as a child process and only host the webview. It already reverse-proxies to the web address (main.go:258-275).
  - (c) Generate the wiring code.
  
  **Recommendation:** (a). The desktop window already loads the same HTTP console, so (b) is a cheap fallback.
  
  ### F4 `scanner-monolith`: the largest package in the module, flat, with a hand-ordered registry
  **Severity:** major. It is new relative to the brief.
  
  **Evidence.**
  - 148 non-test files and 67,334 lines, plus 180 test files and 39,683 test lines. 45 files start with `checks_` and 18 with `infra_`.
  - `ActiveScanner` has 104 methods across 21 files (struct at scanner.go:24-136). Check functions are methods on it (`cc.Scanner.checkJWTWeak`, check_registry.go:20), so every check can reach all scanner state.
  - The registry is a hand-ordered append of slices named after delivery history rather than by domain: `RemainingCheckDescriptors` (checks_remaining.go:1010), `FinalCheckDescriptors` (checks_final.go:481), `DOMExtraCheckDescriptors`, and the comment "Task 6 slices" (check_registry.go:26).
  - A catalog miss panics at startup (`descriptorWithTier`, check_registry.go:56).
  
  **Consequence.**
  - Every check change rebuilds and retests 11 dependent packages, about 133k test lines. scanner alone is the roughly 8-minute shard.
  - Ownership of a family is unclear.
  - Two checks cannot be kept from sharing private helpers. For example, there are two private `headerValue` functions (checks_headers.go and core/capture_request_params.go).
  
  **Options.**
  - (a) Split checks into `scanner/checks/<family>` subpackages. Each family exports `Descriptors()` against a narrow `CheckContext` interface (send, baseline, store, findings) instead of `*ActiveScanner`.
  - (b) Keep one package but reorganise files and the registry by domain.
  - (c) Do nothing.
  
  **Recommendation:** (a), one family at a time, starting with the self-contained ones (takeover, cookie attributes, password reset at 1,944 lines). The first step is to define the narrow context interface.
  
  ### F5 `web-server-god-object`: what actually blocks the `websplit` bead
  **Severity:** major. This refines `burpsy-react-ui-websplit`.
  
  **Evidence.**
  - `web.Server` (server.go:41-310) has **93 fields** and **517 methods** across 125 files. 36 `With*/Attach*/Set*` setters do the wiring. 22 files hold their own mutexes.
  - 26 of the 125 files, 8,864 lines, contain no handler at all. That logic is not about HTTP:
    - `liveaudit.go`: 1,659 lines and 81 functions of scan orchestration. Its header says it mirrors `crates/web/src/routes/liveaudit.rs`.
    - `diff.go` (485 lines), `intruder_send.go`, `events.go`, `extension_services.go`.
  - cmd/burpsy has to build the HTTP server to get a live audit (`webServer.StartLiveAuditSweep`).
  - `mcp` imports `web` only for the manifest metadata (`web.MCPRoutes`, `MCPSchemaFor`), so the thin `burpsy-mcp` client links all of web's dependencies.
  
  **Consequence.** Moving handlers into subpackages stalls on access to the 93 fields. The obvious workaround is to pass `*Server` into the subpackages, which keeps the coupling and only moves files.
  
  **Options.**
  - (a) Move application services out first: live audit into a `scanner`-level or `app` service, and the manifest into a leaf package `web/routes`. Then give each feature subpackage a small `Deps` struct.
  - (b) Split handlers first and pass `*Server`.
  - (c) Use a separate `Server` per feature, each with its own mux.
  
  **Recommendation:** (a). The manifest leaf alone removes mcp → web, and it removes the restated risk vocabulary in agent/policy.go:10-11, which says it "must not import the console".
  
  ### F6 `misplaced-primitives`: four shared building blocks live in the wrong package and invert the layers
  **Severity:** major. This is the cause behind most of the layer inversions in §1.
  
  **Evidence.**
  
  | Building block | Where it lives | Who needs it | Notes |
  |---|---|---|---|
  | Rate limiter (`RateLimit`, `AutoThrottle`, `RateLimiter`) | intruder/limit.go:68/242/276 | crawler, pool | The file imports only the standard library |
  | Insertion-point enumeration (`InsertionPoint`, `EnumerateWith`) | inside the BCheck language package, bcheck/insertion.go (3,047 lines) | scanner, intruder, web | 150 references to `bcheck.InsertionPoint`, 33 to `EnumerateWith` |
  | Capture/ingest pipeline (`Capture`) | scanner/capture.go:82 (575 lines) | proxy, crawler | |
  | HTTP message parsing (head.go, dechunk.go) | httputil, which also contains an HTTP/3 transport (h3.go, quic-go) | everything | Because httputil imports http2, core cannot use it |
  
  That last row is why the message helpers are duplicated (F11).
  
  **Consequence.**
  - Changing the scanner retests proxy and crawler.
  - The insertion-point semantics that Intruder uses depend on BCheck.
  - Each workaround adds a copy instead of fixing the layering.
  
  **Options.**
  - (a) Extract leaf packages: `internal/ratelimit`, `internal/insertion`, and `internal/httpmsg` (head, dechunk, header lookup). Have proxy and crawler depend on a `core.ExchangeSink` interface that the wiring code (F3) fills with `scanner.Capture`.
  - (b) Use type aliases as a transition step.
  - (c) Leave them.
  
  **Recommendation:** (a), with aliases left in place for one round. These are mechanical, stay out of hot code paths, and reduce scanner's dependents from 11 to about 4 (web, persist until F2 lands, the cmds).
  
  ### F7 `ts-contract-duplication`: the generated typed client has no production callers, and the API types are written by hand
  **Severity:** major.
  
  **Evidence.**
  - `ui/src/lib/api-schema.d.ts` is 14,254 lines generated from the manifest. Its only importer is `typed-api.ts`, which `typed-api.test.ts` is the only file to import. No page or library module uses `typedApi`.
  - Production code makes **235** hand-typed `api<T>(url)` calls (api.ts:276).
  - There are **633** exported TS types/interfaces in lib/, pages/ and ui/, including 4,426 lines across 9 `types*.ts` files. They say things like "Mirrors api_project_open.go's projectListResp" (types.ts:151/163).
  - Business logic is also mirrored. 19 TS files describe themselves as mirroring Go: scope containment (history.tsx:163 mirrors `core.Scope.Contains`), JWT decoding (message-views.ts:209), validation that copies the server's 400 responses (extractors.ts:115, form-schemas.ts:71), and the gate resolver (api.ts:45, already filed as `routeresolve`).
  
  **Consequence.** A Go field rename passes `tsc`, because the hand-written type still compiles, and breaks at runtime. The generated contract costs CI time and protects nothing.
  
  **Options.**
  - (a) Move callers to `typedApi` one page at a time, delete each hand type as it is replaced, and add a guard script that rejects new `api<T>("/api/...")` calls.
  - (b) Have the generator emit named aliases (`ApiTypes["GET /api/projects"]`) so `api<T>` keeps working but T comes from the generated file.
  - (c) Delete the generated client.
  
  **Recommendation:** (b) as a quick win, then (a). For mirrored logic, let the server decide where a call per keystroke is acceptable (scope check, validation). Keep a TS copy only with a shared test-vector file that both sides run.
  
  ### F8 `switch-fanout`: one scanner switch has to be edited in 9 places across 6 files, under 3 spellings
  **Severity:** minor. It is mostly test-guarded, but it drives F2 and F7.
  
  **Evidence, tracing `CheckCookieAttributes`:**
  - scanner.go:501 (the field)
  - the registry's `enabled` closure
  - audit_engine.go:194 (the family list) and :393 (a hand-written `zeroFamilies` switch case, :306)
  - api_scanner_config.go:94 (view struct), :279 (to-view), :336 (key map), :545 (apply)
  - types.ts:92
  - scannerlaunch.tsx:43 (label and hint)
  
  The three spellings are `CheckCookieAttributes` (which is also the on-disk key, F2), `check_cookie_attributes`, and the TS key.
  
  **Recommendation:** One declarative table in scanner, `[]Switch{Field, Key, Family, Default, Label, Hint}`. Generate from it the view mapping, `zeroFamilies` (or replace it with reflection over the table), the persisted keys (F2) and a generated `scanner-switches.ts` that the launch page renders. The alternative, keeping it hand-written plus tests, is the current state.
  
  ### F9 `route-statements`: one route is declared four times, and the risk taxonomy three times
  **Severity:** minor. It is well guarded, so this is mostly about the cost of adding a route.
  
  **Evidence.**
  
  | Declaration | Where | Count | Guarded by |
  |---|---|---|---|
  | Route registrations | server.go | 190 `s.route(...)` calls | the manifest test parses server.go's syntax tree (route_manifest_test.go:65) |
  | Manifest | route_manifest.go:105 | 190 patterns, 261 route-verb pairs | |
  | Request schemas | route_schemas.go | 193 verb entries | required for every mutating verb |
  | MCP grouping | mcp/groups.go | everything except 15 `notExposed` entries (:498) | an "exactly one grouped tool" test |
  | Generated client files | api-schema.d.ts, gated-routes.ts | regenerated after each change | |
  
  On top of that come the hand-written type and call (F7). The risk classes are restated in agent/policy.go:10-17 and generated into gated-routes.ts.
  
  **Recommendation:** Register routes from the manifest, adding a handler field to `route`, so server.go no longer lists them separately. Move the manifest and risk vocabulary into a leaf package (F5a).
  
  ### F10 `persistence-compat-policy`: two backward-compatibility strategies that contradict each other, and no record of the decision
  **Severity:** major.
  
  **Evidence.**
  - migrate.go:19-21 has one migration step, "additive schema", which is `user_version` 1. migrate.go:30-34 refuses to open a newer database.
  - Schema changes have instead been made with parallel tables. `SaveScope` writes `scope_rules_v3`, `_v2` and the legacy `scope_rules` on every save (persist.go:1258-1304), "for one reason: an older build reads only that table" (persist.go:1252-1257). Reads fall back v3 → v2 → v1 (:1320-1357).
  - The schema has 20 tables and 38 `addColumn` calls.
  - 27 settings are unversioned JSON blobs (`proxy.options`, `network.settings`, `scanconfig.overrides`, and others).
  - Message bodies are durable in two places: SQLite `messages.raw` and the segment log (`-capture-dir`).
  - DATA-MODEL.md has no section on versioning or migration.
  
  **Consequence.** The first real step-2 migration makes every older build refuse the file, so the triple-write downgrade protection becomes dead weight. Until then each change grows another `_vN` table. The blobs evolve with no version and no defaults-on-load rule, which is how F2 happened.
  
  **Options.**
  - (a) Write an ADR: SQLite `user_version` is the only compatibility mechanism. Opening is forward-only. Before a migration, the file is copied to `<db>.bak-v<N>` (backup support already exists in `api_backup`). Every blob carries `{"v":N}` and is decoded onto defaults. Drop the `_v2`/legacy writes in a step-2 migration.
  - (b) Formalise mirror-for-downgrade as the policy.
  - (c) Leave it ad hoc.
  
  **Recommendation:** (a). It also decides whether the segment log or SQLite is the durable source for bodies.
  
  ### F11 `http-message-dup`: message parsing is re-implemented in many packages
  **Severity:** minor (correctness risk).
  
  **Evidence.**
  - Despite `httputil.SplitHeadBody` and `HeaderValue` (httputil/head.go), there are 9 private head/body splitters: sender/connpool.go, web/api_browser_reissue.go, scanner/readable.go, core/capture_request_params.go, web/api_sequencer_capture.go, intercept/intercept.go (×2), web/api_repeater_graphql.go, session/macro_step_from_request.go.
  - There are about 8 private header-value lookups.
  - 106 sites in 61 files split on `"\r\n\r\n"`.
  - There are 4 chunked-body decoders: httputil/dechunk.go:16, core/edit.go:397, web/api_types.go:499, proxy/proxy.go:3235.
  
  **Consequence.** Different modules frame the same message differently. That makes request-smuggling and desync disagreements between proxy, scanner and history more likely.
  
  **Recommendation:** Use the `internal/httpmsg` leaf from F6, then a lint/AST test that flags new `"\r\n\r\n"` splits outside it.
  
  ### F12 `unenforced-boundaries`: the Rust crate boundaries became conventions, and some written reasons are already false
  **Severity:** minor. This refines `importbound` and `egressdial`.
  
  **Evidence.**
  - The golangci set is only staticcheck and errcheck (scripts/ci/golangci.yml:16-18). There is no depguard or architecture test.
  - A rationale comment is already false: web/redirect_cookies.go:15 says "internal/session imports internal/sender". `go list` and grep show session imports only `jsexec`; I confirmed that by finding the `internal/jsexec` import in session/actions.go and finding no `internal/sender` import in any session file.
  - Copied vocabularies show where the layering forced a copy: blindxss/listener.go:34, crawler/crawler.go:513/603, agent/policy.go:11, core/findings.go:195.
  - Clients built outside `sender`: scanner/triage.go:110 (an LLM endpoint), scanner/checks_pwreset.go:1657 (a mailbox, `Proxy: nil`), web/api_collaborator_health.go:76/105.
  
  **Recommendation:** Extend the `importbound` test into a layer table, so each package lists which layers it may import. Include the new F6 leaves, "proxy/crawler must not import scanner", and "mcp/agent must not import web". Then the copies can be deleted.
  
  ### F13 `generated-artifacts`: five code generators across four toolchains, and one diverged copy
  **Severity:** minor.
  
  **Evidence.**
  - The committed `dist/app.js` (2,751,270 bytes) is touched by 34 of the 664 visible commits, and the pack is 25.8 MiB.
  - The generators:
    - `scanner/tools/gen_catalog.py` (Python, writes catalog_data.go, 3,698 lines). It differs from `crates/scanner/tools/gen_catalog.py` (145 lines against 141).
    - `cmd/openapi-dump` (Go) piped into `gen-api-types.mjs` (Node).
    - `gen-gated-routes.ts` (Bun).
    - `gen-tokens.mjs`.
    - `cmd/bcheck-bundle`.
  - There are zero `go:generate` directives. CI checks freshness only for the UI outputs (go.yml:338-352). Nothing checks that catalog_data.go or the bundled corpus are fresh.
  
  **Options for the bundle.**
  - (a) Keep committing it, because `go install` and `go:embed` need it.
  - (b) Build it in CI and release only, embedding a stub otherwise.
  
  **Recommendation:** Keep (a); the policy and the freshness gate work. Add one `scripts/gen-all.sh` with `--check` covering every generator, and run it in CI.
  
  ### F14 `adr-coverage`: none of the structural decisions has an ADR
  **Severity:** minor.
  
  **Evidence.**
  - docs/adr has 0001 (how parity is measured), 0002-0004 (scanner check semantics) and 0005 (a merge exception).
  - None covers: the Go port and the role of `crates/`; memory-authoritative storage with SQLite as a mirror; the committed bundle; JSON-RPC child-process plugins with an exact-match protocol version; MCP as an HTTP client derived from the manifest; the compatibility policy (F10).
  - 291 "Why" sections or rejected-alternative notes in non-test Go comments hold these decisions instead. As F12 shows, comments go stale.
  
  **Recommendation:** Backfill ADRs 0006-0011 from those essays, about one page each. Add an ADR checkbox to the review-gate for changes to the manifest, the schema or the package layering.
  
  ### F15 `vulnapp-in-module`: the vulnerable target app lives inside the product module
  **Severity:** minor.
  
  **Evidence.** `internal/vulnapp` is 16,428 lines. Only `cmd/demo-target` and `cmd/crawl-scan-demo` import it, so it is not linked into the product binaries. Like `cmd/xsschallenge`, it still adds to `go vet`, lint and the affected-test runs.
  
  **Recommendation:** Move it to `testdata/` or a separate module when convenient. Low priority.

  ## 3. Refactoring roadmap (each step merges on its own; the product stays shippable)
  
  **Round 0: guardrails, no behaviour change.**
