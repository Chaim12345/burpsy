## 1. The TLS-passthrough runtime surface (`c5bb50e` + `7cbca74`)

Burp configures its TLS passthrough list live; burpsy's was **CLI-flag-only**, so the
runtime surface closes that gap end to end:

- **proxy** (`c5bb50e`): `TlsPolicy.Passthrough()` returns a **copy** under RLock (a shared slice
  would race a concurrent `AddPassthrough`); `RemovePassthrough` matches **exact strings** —
  `*.bank.test` and `bank.test` are deliberately different rules, and wildcard-equality removal would
  delete one the operator did not select. Pinned by `TestRemovePassthroughRemovesOnlyTheExactPattern`.
- **persist**: `SaveTlsPassthrough`/`LoadTlsPassthrough` keep the list as **one JSON setting value**,
  not a table — it is one small ordered list with no per-row identity, and the whole-list save is
  deliberate because the endpoint mirrors the policy's live list after every mutation, so an
  incremental mirror API would let the durable copy drift from what the proxy obeys.
- **wire**: `GET/POST/DELETE /api/proxy/passthrough` on the shared `TlsPolicy`. Verb
  dispatch precedes the nil-policy guard — 503 means "this capability exists and is unavailable",
  so a policy-less server still answers 405 to verbs it does not implement. Removal answers
  **404** for an absent pattern instead of quiet success (a double-clicked remove would otherwise
  look like two rules existed). Every mutation returns the confirmed list.
- **cmd**: `main` attaches the *same* policy object the proxy matches against (two copies would let
  Settings render a list the proxy no longer honours) and re-applies persisted patterns over
  flag-configured ones on startup, deduplicated (`*.bank.test` arriving by both doors renders once).
- **UI**: Settings → TLS passthrough section with list/add/remove, sharing Scope's table idiom.

Live-verified against a running server including **restart persistence** via `-db`.

## 2. One headless browser for the whole scanner package (`7ec97c3`)

Every test that needed a browser used to build its own `NewLazyBrowserProvider`, so a full
`internal/scanner` run paid **five** Chrome process starts. `domexec` already solved this in its
own tests via TestMain (8.9s total); the scanner now enjoys the same `sharedBrowserProvider()`.

Sharing is safe because `Browser` hands out an **isolated tab per call** (the `newTab` contract),
so concurrent or sequential checks never see each other's instrumentation state. `TestMain` owns the
close — **not** `t.Cleanup`, which would close Chrome when the *first* test finished and leave every
later DOM test observing a dead process, which reads as zero observations, which reads clean. The
closed-browser guard test keeps a private provider deliberately. `lazyBrowser.Close` is now
idempotent because the provider is released through two doors.

Measured: 404.9s → 382.7s (729 tests green). The remaining bulk is *real* per-endpoint
browser coverage — no sharing can remove that.

## 3. DOM engine decoupled: `Options.RemoteURL` (`e39b230`)

`NewBrowser` could only exec-launch Chrome. `Options.RemoteURL` attaches to an already-running CDP
server (`obscura serve`, `lightpanda serve`); setting both `RemoteURL` and `ChromePath` is refused
as the configuration contradiction it is. `BURPSY_DOM_REMOTE` points the whole scanner + domexec
suite at a running server, so any CDP engine runs the same sink-by-sink and vulnapp assertions with
zero test changes.

**Why every remote check dials a FRESH connection (a correctness find, not a micro-optimisation):**
measured against obscura serve, fast create/navigate/cancel cycles over ONE connection lose their
server-side sessions (`executor for page-N-session doesn't exist`), surfacing downstream as zero
observations — a false negative. Nondeterministic: two runs, ten failures each, different tests. A
fresh connection per check is the shape these servers are built for (each gets its own thread and V8
isolate), and was 20/20 stable where shared tabs were 10/20. The `BURPSY_DOM_REMOTE` scanner hook
lives in `runtime_shared_test.go`, folded into the validation work that led to `96bcf1a`.

## 4. Parity under stress, and the two engine defects it surfaced (`96bcf1a`)

Full vulnapp detection suite under obscura serve — the real `ActiveScanner` pointed at
`internal/vulnapp`, every declared vulnerability seeded, safe counterpart audited in the same run:

| Measure | Chrome | Obscura (final) |
|---|---|---|
| Catalog rows demonstrated | 160/160 | **160/160** |
| Rows missed | 0 | **0** |
| Safe-counterpart quietness (false positives) | clean | **clean** |
| Request-budget test | ✅ | **✅** |
| Stress (detection + quiet ×3) | — | **✅ 3/3 (197s)** |

Two real engine defects were found by running this suite — not by reading code — and fixed in the
harness, not worked around in the checks:

**a. `window.name` was reset by obscura on navigation → 11 silent reflected-DOM rows.** The old
plant sequence was `about:blank` → set `window.name` → navigate, relying on the browser carrying
`window.name` across navigations (HTML-spec behaviour Chrome honours). Obscura rebuilds its window
object per document, so the canary vanished and all 11 `window.name`-sourced `(reflected DOM-based)`
rows went dark (the first fix round demonstrated only 149/160, 11 missed). The canary is now injected
at the **end of the preload script** that runs before the page's scripts on every engine — no
cross-navigation persistence needed, observationally identical to arriving with an attacker-set
`window.name`.

**b. Obscura's bootstrap calls instrumented platform functions → false positives on safe endpoints.**
Obscura implements location/URL handling in a JS bootstrap layer, so reading `location.search` routed
through `JSON.parse` and reported a *Client-side JSON injection* on provably safe endpoints. The
filter is **structural, not textual**: every observation's stack begins with two `<preload>` frames
(record + wrapper), so the first frame outside the harness is whoever actually made the call —
`<obscura:` means engine-internal (drop); a page frame means the page (keep). Chrome has no such layer
and is unaffected (verified 20/20 unchanged).

**c. The `executor for page-N-session doesn't exist` noise** — root-caused (chromedp `browser.go`):
it logs when a `Target.detachedFromTarget` deletion arrives for a session already removed, which
Obscura delivers after teardown. Benign by construction (the handler logs-and-deletes an absent map
entry). Suppressed in remote mode with a filtered error logger that stays attached to every per-check
connection; the earlier flaky failures were the shared-connection bug in §3, not this.
