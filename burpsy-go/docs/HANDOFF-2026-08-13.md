# Handoff — scanner coverage measurement rebuilt on runtime evidence

Written 2026-08-13. Branch `ui-react-comparison`.

## The one thing to understand first

This session replaced how scanner coverage is measured, because the previous measures all measured
something else:

| Metric | What it actually said | Why it misled |
|---|---|---|
| `Runnable()` = 183/183 | `Run != nil && DeclineReason == ""` | A non-nil function pointer. Cannot distinguish a detector from a stub. |
| statement coverage 76.6% | lines executed by tests | **Rose when tests asserting checks REFUSE to run were added.** Executing a capability guard is not exercising a detector. |
| symbol-reference grep | nothing reliable | Produced straight false negatives; called functions unreferenced that the suite does execute. |

None answered: *when this scanner is pointed at something that really is vulnerable, does it say so?*

`internal/scanner/runtime_coverage_test.go` now answers exactly that and nothing else. It starts the
deliberately vulnerable app in `internal/vulnapp`, seeds real exchanges over real HTTP, runs the real
`AuditWithin`, and asserts three things: every declared vulnerability is reported; the **safe**
counterpart of each reports nothing for that row; probes sent per endpoint is >0 and under budget.

## Honest coverage claim

**21 of 183 catalog rows (11.5%)** have an end-to-end runtime demonstration against a live target,
proven across 23 vulnerable endpoints — XSS (reflected) and SQL injection are each demonstrated at
two endpoints, and the distinct-row figure is the one to quote. **19 of the 21 also have a
false-positive counter-example**: a safe endpoint that reflects the same input without the defect and
must stay silent, audited in the same run as its vulnerable twin so silence cannot come from a check
that simply never fired.

The rows, by how they are proven:

| How proven | Rows |
|---|---|
| Active probe through enumerated insertion points | SQL injection, XSS (reflected), File path traversal, OS command injection, Open redirection (reflected), HTTP response header injection, XPath injection, LDAP injection, Server-side template injection, XML external entity injection, XML entity expansion, Link manipulation (reflected), Unidentified code injection, SSI injection |
| Headless browser (Chrome, taint-instrumented sinks) | XSS (DOM-based), JavaScript injection (DOM-based), HTML5 storage manipulation (DOM-based), Cookie manipulation (DOM-based), Open redirection (DOM-based) |
| Passive, no probe needed | CORS: arbitrary origin trusted, Database connection string disclosed |

Separately, one second-order row is demonstrated end-to-end in `stored_lifecycle_test.go` rather than
in the manifest: a canary planted in `/comment` is confirmed only after the scan-end re-fetch sees it
rendered by `/comments`. It is not in the manifest because an informational "input returned in a
later response" row has no meaningful *safe* twin — escaping does not change the fact that the value
came back — and the manifest's pairing guard rightly requires one.

**The other 162 rows have no runtime evidence.** They are registered and unit-tested, which is a
weaker claim. Do not restate "183 runnable" as a coverage figure; `runtime_coverage_test.go`'s own
header explains why that number cannot mean what it looks like. The 21 is pinned by
`wantDemonstrated` in that file, so removing a manifest row fails the suite rather than quietly
lowering the published number.

## Defects found and fixed

Each was found by running the scanner for real, not by reading it.

1. **False positive at `certain` confidence.** `ClassifyEvaluation`'s reflection guard required the
   payload to appear *verbatim*, so an application that HTML-escapes its output correctly had its
   escaped echo credited as command *evaluation*. `/login` and `/redirect` were reported as OS
   command injection. The better a target's output encoding, the more confidently it was libelled.
   Now subtracts the echo from the raw, `html.UnescapeString`d and `url.QueryUnescape`d body forms
   (`echoComparableForms`). Enumerating encoder styles was the first attempt and failed on
   `net/http`'s `&#34;` vs `&quot;` — decoding beats enumerating.

2. **False negative that scaled with target quality.** Signature matching was a raw substring
   search, so a page echoing `root&#x3a;x&#x3a;0&#x3a;0` was missed — traversal and SQL-error
   detection failed on precisely the targets that encode output properly. `matchableForms` now
   matches the unescaped form too, mirroring ZAP's `unescapeHtml4`. ZAP has a regression test for
   this exact case; we now do too.

3. **Five checks guessed the parameter name.** `checkSQLi`, `checkXSS`, `checkPathTraversal`,
   `checkOpenRedirect` and `checkHeaderInjection` built probes with
   `appendQueryParam(path, "test"/"xss"/"file"/"redirect"/"burpsy_hi", payload)`. They only fired if
   the application's vulnerable parameter had that exact name — and when it *did*, appending a second
   copy still tested nothing, because `Query().Get` returns the **first** value. All ported onto
   `ProbeHarness` insertion points. This is the class of bug ZAP's architecture makes
   unrepresentable: `AbstractAppParamPlugin` owns the parameter loop and hands each rule
   `scan(msg, paramName, value)`, so a rule cannot name a parameter.

4. **The XSS script-breakout marker was a substring of its own payload.** `alert(<canary>)` survives
   HTML escaping untouched, so a correctly-escaping endpoint confirmed a breakout. Now
   `'-alert(<canary>)-'`, including the quotes — the only characters escaping transforms. *Still
   partially open, see below.*

5. **Ten stored rows were wired, counted as coverage, and could never fire.**
   `ObserveStoredCanaries` was called only from tests. Nothing in `audit_engine.go`,
   `checks_stored.go`, `liveaudit.go` or the proxy fed it, and two comments asserted otherwise. Now
   called from `auditItem` before dispatch, guarded by an **engine-level** test
   (`TestAuditingAnExchangeFeedsItToTheStoredLedger`) — a ledger unit test cannot catch a missing
   call site.

6. **The OS-command marker was the compile-time constant `bsycmd42`.** `NewProbeHarness` fetches a
   live baseline and `ClassifyEvaluation` returns Inconclusive when the marker is already in it, so
   once any endpoint rendered a stored copy of a previous scan's marker the check went permanently
   silent on a genuinely injectable target. Now `newProbeCanary("bsycmd")`.

7. **`rawHeaderValue` split only on CRLF.** Two of three `headerInjectionSeparators` are a bare CR
   and a bare LF, so six of nine probes per insertion point could not confirm. Now splits on LF and
   prefers the *last* match, because response splitting injects its header after the legitimate one.

8. **Two commands were invisible to the gate.** `cmd/demo-target` and `cmd/live-test` each had a
   nested `go.mod` (`module X / go 1.19`, zero deps), so `go build ./...` and `go vet ./...` never
   saw them. Removed; both now compile under one module.

9. **A 13 MB compiled binary was staged for commit** (`burpsy-go/crawl-scan-demo`). Removed;
   `.gitignore` now enumerates both build locations for every command.

10. **`docs/SCANNER-COVERAGE.md` asserted a fact and its negation** — "nothing is declined" in the
    header, above a 141-row declined table claiming `OS command injection` has no native evaluator
    while `checks_injection.go` implements it. The stale half is deleted rather than annotated.

The runtime corpus also found a real bypass in a handler I had written as the *safe* half of a
false-positive guard: a naive same-origin check accepted `/\evil.example/`, which browsers normalise
to `//evil.example/`. That is why `/\a` is in Burp's recovered prefix bank.

## Known gaps — read before trusting a clean result

- **`InjectionEvidenceInconclusive` is silence, not a caveat.** The type documents "NOT a clean
  result" and nothing honours it: `BestEvidence` returns `confirmed=false` and every caller does
  `if !res.confirmed { return nil, nil }`. So any argument that a conservative choice "only
  downgrades to Inconclusive" is an argument that it downgrades to nothing. Fix: surface the count on
  the no-finding path (an `AuditOutcome` field, or an informational finding). Detail at
  `infra_injection_evidence.go`'s `InjectionEvidenceInconclusive`. **This is the top of the list.**
- **Stored rows cannot complete in a batch audit.** Planting happens during the audit; every captured
  response predates it. Batch mode yields Outstanding canaries and no findings. The live-proxy path
  can close the cycle; re-fetching planted URLs at scan end would close it for batch too. Detail in
  `checks_stored.go`'s header.
- **Out-of-band has no Outstanding state.** `oobCheck` does `time.After(5s)`, reads interactions once,
  returns. Every later callback is dropped and reads as clean. Nuclei solves this with a dual-tier
  cache that survives scan completion; that is the shape to copy.
- **The XSS script marker is still a substring of its payload.** Mitigated, not fixed: the row is now
  gated on a markup Content-Type (`rendersAsMarkup`), which removes the plain-text false positives.
  A verbatim reflection into `text/html` would still satisfy the marker. Separate canaries for the
  payload and the marker would close it properly.
- **Runtime config omits ~80 rows.** `CheckDOM` (48, needs Chrome), `CheckExtendedActive` (22, of
  which only ~5 need the network — the other ~17 should be enabled here), `CheckStored` (10).
  Enumerated in `runtimeScanConfig`'s comment.
- **Three checks still guess a parameter name**: `checkLinkManipulation` (`burpsy_link`),
  `checkCodeInjection` (`burpsy_ci`), `checkSSIInjection` (`burpsy_ssi`). Same defect as the five
  already ported; same fix.

## Closed after adversarial review

A `critic` agent reviewed the session's decisions and returned REVISE with 20 findings. The ones
worth recording as closed, because each was a real defect rather than a style note:

- **The corpus could not discriminate the bug that motivated the rewrite.** `/products` iterated every
  query parameter, so restoring `appendQueryParam(path, "test", payload)` kept every assertion green,
  and three fixtures were still named after the deleted constants (`xss`, `test`, `file`). Renamed to
  `greeting`/`sort_col`/`doc`, and `products` now reads one named parameter. Verified: reverting the
  port fails both SQL rows.
- **`/products` modelled the payload bank, not a database** — it branched on `order by 999`,
  `or '1'='1`, lowercased copies of the scanner's own probe table. Removed; only the quote-balance
  rule remains, which is a property of SQL syntax.
- **`SCANNER-COVERAGE.md` asserted a fact and its negation**, and three family headings disagreed
  with their own totals table. Reconciled.
- **`sqli.go` was 80% dead code** — the probe table, evidence bitmask and decision table had no
  consumer after `checkSQLi` was deleted, and `internal/vulnapp` had grown branches matching its
  literal payloads. Reduced to `sqlInjectionIssue` and `responsesDiffer` (four live callers).
- **`cmd/crawl-scan-demo` lied twice** — cited deleted functions, and justified a divergent second
  vulnerable target with "cmd/demo-target is its own module and cannot be imported here", false since
  the nested go.mod removal. Now uses `vulnapp.Handler()` and seeds from the manifest.
- **`offlineSignatureScan` turned a capability refusal into a clean result.** Now returns the
  tentative finding when a signature is present and an *error* when it is not. Two dispatch-accounting
  tests were rewritten to audit a live target, because their premise that three active checks all
  "ran" offline was only satisfiable while those checks pretended.
- **`buildRawResponse` truncated the seeded baseline** with a single `Read`; now `io.ReadAll`.
- **`headerLookup` was dead**, kept alive by its own test. Both replaced by a `rawHeaderValue` test.

## Architecture question that was asked and answered

Whether to move to an event-driven / state-machine design. **All three references were mapped and
none is event-driven for check execution.** Burp, ZAP and Nuclei are all synchronous/concurrent
dispatch plus **polling** for deferred evidence, with pending state in a plain registry — Burp's
`Zrm7` follow-up on a ~1000 ms timer, ZAP's OAST `scheduleAtFixedRate`, Nuclei's background
interactsh poller. An
event loop is not the missing piece; a **pending-evidence registry with a poller and late-arrival
tolerance** is, and it is a two-file change. Two things worth copying from Nuclei: that late-arrival
cache, and **request clustering** (`TmplClusterKey` / `ClusterExecuter` send one request and match
all operators) — this scan sends 3920 probes across 16 endpoints, mean 245.

Reference checkouts used: `/root/ref/{zap-extensions,zaproxy,nuclei}`. Data point worth keeping: ZAP
has **51 active scan rules and 51 unit test files, exactly 1:1**.

## Where to pick up

Items 1-5 of the previous list are done: the `Inconclusive`-is-silence gap is closed (an undecided
check now reports `Unmeasurable` rather than silence), the pending-evidence registry with a poller
and late-arrival tolerance exists and `oobCheck`'s `time.After` is gone, the XSS row is gated on
Content-Type with a marker that is no longer a substring of its payload, the manifest grew by SSTI /
XXE / LDAP / XPath / a stored pair, and all three guessed-parameter checks were ported onto real
insertion points.

What is left, in the order it pays:

1. **Demonstrate more rows.** 21 of 183. Each new manifest pair is a real increment to the only
   number that means anything; anything else is registration. The cheapest remaining candidates are
   the rows already wired behind `CheckPassiveAnalysis` — 28 analysers needing no probe at all.
2. **The out-of-band rows are unit-tested, not demonstrated.** `oob_channel_test.go` proves a late
   callback is still correlated using a fake channel whose timing the test controls. That is the
   right test for the *timing* property, but no row behind `CheckOutOfBand` has ever been shown to
   fire against a real target from this repo. Wiring `WithOOBProvider` into a caller and running one
   real interactsh scan would settle it.
3. **The 26 stored rows share one demonstration.** Only the "input returned in a later response"
   path is proven; the nine context-specific spellings (inside `<script>`, in an `href`, in a form
   `action`) are unproven, and each needs a rendering endpoint that puts the canary in that context.
   Note the honest limitation first: the context matchers key on *where* the token appears, not on
   whether a breakout survived, so an alphanumeric canary cannot demonstrate stored XSS on its own.
   Burp sends a second breakout payload once a sighting exists. That is the missing half.
4. **`DispatchScopeInSessionPerRequest` is still unreachable** — the last of the seven. Nothing is
   bound to it, so it is honestly declined; check that is still true before binding anything.
