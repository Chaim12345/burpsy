  ## Why burpsy missed them, and the fix
  - **Why it missed them:** burpsy sent no null-byte payloads at all. On img L5 there was a second problem: the allowlist answers any value it does not recognise with nothing. So burpsy's first probe, a bare random token, never came back, and no attack payload was ever chosen for that parameter.
  - **The fix:** after every other XSS attempt on a parameter has failed, the check now appends a null byte and a probe to the parameter's original value. The original value is the one value the app is known to accept, so the part a null-truncating check reads is exactly that.
    - Per parameter this costs one observation probe, then at most 3 payloads chosen for where the value lands.
    - A breakout is confirmed exactly as for an ordinary payload, either from the raw response or by rendering the fragment in the browser as the page's script would.
    - The finding names "null-byte truncation" as how the breakout got through.
    - A parameter with no original value is not probed this way.
    - A reflection seen only through this variant is not counted unless the breakout is confirmed, so it does not trigger the separate browser-confirmation step.
  - **One change to existing wording:** findings carried by a variant used to say "…the encoded one did". They now say "…the variant named in the evidence did".
